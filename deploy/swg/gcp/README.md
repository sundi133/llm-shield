# Shield SWG on GCP

Two scripts here, for two different customers. Running the wrong one is not a
small mistake, so start with the question rather than the command.

**Does the traffic you want to screen already pass through a gateway that
decrypts it?**

| | Script | Deploys |
|---|---|---|
| Yes, there is a Zscaler / Netskope / Blue Coat / Cisco WSA / Forcepoint | `deploy.sh` | The adapter alone. Point the existing gateway's ICAP service at it |
| No, and the clients are GCP workloads in a VPC | `deploy-mode-a.sh` | Squid plus the adapter, inside that VPC |

If unsure, ask the host:

```bash
docker run --rm --pid=host shield-icap preflight
```

Installing a second interception point where one already exists buys nothing
and costs two forged certificate chains and two bypass lists to keep in sync.

## `deploy-mode-a.sh`, the bundled gateway

```bash
./deploy-mode-a.sh <project> <region> <network> <client-cidr>
```

```
GCE / GKE client            swg-proxy MIG (no external IP)
HTTPS_PROXY ----- ILB:3128 -> squid :3128 --.
+ CA trusted                                 | docker bridge, never
                                             v published to the host
                                            shield-icap :1344
                                              |
                           Cloud NAT <--------'
                              |
                              v
                api.openai.com, api.anthropic.com, ...
                api.guardrails.votal.ai  (policy bundle + telemetry)
```

Before it will run, two secrets need a version. The CA is generated by you: the
script will not create one, so the private key is never produced inside
automation or baked into an image.

```bash
openssl req -new -newkey rsa:4096 -sha256 -days 1825 -nodes -x509 \
  -extensions v3_ca -keyout ca.pem -out ca.pem \
  -subj "/CN=Example Corp Internal Inspection"

gcloud secrets versions add swg-ca-pem --data-file=ca.pem
printf %s '<tenant key>' | gcloud secrets versions add shield-api-key --data-file=-
```

Preview exactly what an instance will boot, with no project and no gcloud:

```bash
./deploy-mode-a.sh --emit-startup
```

### Why Squid is here, when `deploy.sh` deliberately excludes it

`deploy.sh` says Squid does not belong in the cloud, for two reasons: a proxy on
a public port is an open relay, and the interception CA's private key belongs
where the users are. Both are true for a laptop fleet dialling in over the
internet.

Neither applies here, because the clients **are** GCP workloads in this VPC.
There is no public port: no external IP, an internal passthrough load balancer,
and a firewall scoped to the client range. And the VPC is already the trust
boundary the CA key belongs in.

So this script covers the case `deploy.sh` does not, and does not replace it.
For remote laptops proxying in over the internet, use neither: that needs proxy
authentication or Cloud VPN, and it is a separate design.

### Three GCP choices with an obvious wrong alternative

**Cloud Run cannot host either half.** ICAP is its own protocol on its own port
and Cloud Run only accepts HTTP. The same is true of Squid.

**Internal passthrough load balancer, not an application load balancer.** An
ALB parses HTTP and would reject a CONNECT-tunnelling proxy stream. Passthrough
hands the TCP connection through untouched.

**Debian, not Container-Optimized OS.** COS ships no gcloud, so fetching a
secret there means hand-rolling a metadata-token call against the Secret Manager
REST API and parsing JSON without jq. The cost of Debian is installing docker at
boot, so an instance is not healthy until NAT egress works.

### A GCP product that looks right and is not

**Secure Web Proxy** is a managed TLS-inspecting proxy where you supply the CA
through Certificate Manager, and for a GCP-native customer it looks like exactly
the right way to replace Squid. It has no ICAP support: its policy engine is its
own URL and TLS rules, with no callout to an external screening service, so it
cannot talk to this adapter. Worth knowing before it comes up in a design review.

## After deploying

Point workloads at the proxy and trust the CA. The bundle variables are not
optional: Python and Node ship their own trust stores and ignore
`update-ca-certificates`, and forgetting them is the single most common cause of
"everything broke after the proxy".

```bash
export HTTPS_PROXY=http://<proxy-ip>:3128

gcloud secrets versions access latest --secret=swg-ca-pem \
  | sudo tee /usr/local/share/ca-certificates/shield-ca.crt >/dev/null
sudo update-ca-certificates
export REQUESTS_CA_BUNDLE=/usr/local/share/ca-certificates/shield-ca.crt
export SSL_CERT_FILE=/usr/local/share/ca-certificates/shield-ca.crt
export NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/shield-ca.crt
```

Confirm policy actually loaded before trusting a quiet console:

```bash
gcloud compute ssh <instance> --zone=<zone> --tunnel-through-iap \
  --command 'curl -s localhost:8081/healthz'
```

`rules: 0` means no policy loaded and nothing will ever block, whatever the mode
says.

It deploys in **monitor** mode: nothing is blocked, everything is reported.
Review what would have blocked, then move a canary group to enforce. An operator
who cannot safely try enforce will stay in monitor forever, so do that early
rather than perfecting the review.

## The limit of this

A workload that ignores `HTTPS_PROXY` reaches the provider directly and is never
screened. There is no error and no log line, because nothing routed through the
proxy in the first place. The same is true of anything speaking HTTP/3, since
QUIC ignores an HTTP proxy entirely.

Until you deny egress on 443 to everything except the proxy, this is a control
against accidental leakage, which is the actual threat model for AI data loss.
It is not a control against someone who has decided to exfiltrate. Be straight
with buyers about which one they are buying.
